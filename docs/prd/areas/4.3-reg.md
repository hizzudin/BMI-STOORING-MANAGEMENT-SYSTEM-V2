# 4.3 REG: module registry, step composer and SPK presets (P0, risk: critical)

> Part of the BMI Stooring System spec (§4 functional requirements, area REG). Core rules, roles, state machines, business rules and decisions: [PRD.md](../../../PRD.md). Section numbers and IDs are unchanged from the single-file PRD v2.4.


Goal: the Planner and System Admin build the steps of each SPK in Create SPK and reuse good sequences as presets, and new modules can be added later without changing the engine.

**Module contract.** Every module, the five current ones and any future one, provides exactly these items through its registry row:

| Item | Meaning | Column |
| --- | --- | --- |
| Code and name | Identity in the designer | `code`, `name` |
| Allowed executor roles | Who may run a step of this module (the System Admin always may) | `executor_roles` |
| Step options | Settings the designer may give each step | `config_schema` |
| Creation section | What the SPK creator fills for a step of this module in Create SPK, and whether it is required (Stock: parts and tyre sizes with quantities, required; Part Purchase: parts to buy without quantity, optional; Mechanic Action and Part Replacement: nothing; Part Check: parts to check with what to check, required; Document: the vehicle document to renew, required). Empty means the step only shows its name | creation\_schema |
| Step screen | The front-end component opened in the SPK workspace | `ui_component` |
| Scope rules | What data of the SPK's vehicle and which master data the module may read or change | `scope_rules` |
| Completion section | What the SPK document prints for the step | `completion_section` |
| Submit behaviour | What happens on submit (Stock cuts stock, Document updates the document) | service handler keyed by `code` |
| Cost contribution | Parts, Labor, Document or None | `cost_kind` |

**Build note.** Do not hard-code the five modules in the engine, the designer, the SPK document, the permission checks or database enums. Build them as the first five registry rows using the same contract a future module will use.

| ID | Verifies | Acceptance criterion |
| --- | --- | --- |
