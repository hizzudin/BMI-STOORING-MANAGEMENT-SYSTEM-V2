## Architecture (no new tables, no migration)

### Port (`ports/spks.ts`): plain data, no Drizzle

```ts
interface SpkListFilter {
  statuses?: SpkStatus[];          // the tab
  mineOf?: { userId: number; roles: Role[] }; // My steps
  search?: string;                 // SPK number, title or plate, contains, any case
  category?: SpkCategory;
  vehicleId?: number;
}
listPage(filter: SpkListFilter, page: { offset: number; limit: number }): Promise<SpkListRow[]>;
countMatching(filter: SpkListFilter): Promise<number>;
listVehicles(): Promise<{ id: number; licensePlate: string }[]>; // the vehicle filter
detail(id: number): Promise<SpkDetailRow | null>;
```

- `SpkListRow` is `SpkRow` plus `currentStep` (sequence number, module, status), `assigneeName`, `creatorName`
  and `creatorRole`.
- Ordering is Urgent, High, Normal, Low, then newest first.
- `findList`, `countList`, `countByStatuses`, `countMine` and `countAllNonDeleted` are removed. The
  Drizzle code moves into `infra/db/spk-gateways.ts`.

### Core (`core/spk/spk-list-service.ts`)

- The tab-to-status map:
  - Active: Active, In_Progress, Pending_Verification, Pending_Amendment.
  - Draft, Pending approval, Rejected, Completed, Cancelled: one status each.
  - All: every status.
- My steps: SPKs with a step that is Open or In_Progress and either assigned to the user, or
  unassigned with one of the user's roles among its executor roles. This is matching data in
  `executor_roles`, not a permission decision.
- The tab counts use the same search, type and vehicle filters.
- Every row's `allowedActions` come from `SPK_POLICIES` (`edit`, `submit`). The page action is `create`
  with spk.create.
- **Waiting on**, from the data that exists:

  | Status | Waiting on |
  | --- | --- |
  | Draft, Rejected, Pending_Amendment | the creator (role and name) |
  | Pending_Approval | "Approvers" |
  | Active, In_Progress | the assignee of the current step, else its executor roles |
  | Pending_Verification | the verifier role of the current step |
  | Completed, Cancelled | none |

  This is written in `specs/design.md` 5.11.
- `detail(actor, id)` returns the header, vehicle, creator, steps (each with status, executor roles,
  assignee, opened, submitted and verified time), the spk_approvals rows (stage, action, name, role,
  time, note, self-approved) and the costs (labour, parts, document, stooring, total).

### HTTP

One `SpksController`:

- `GET /spks/:id/detail` (spk.view);
- the existing routes.

The second controller and filter are removed.

### Shared

- The `actor.ts` copy is removed.
- The list response gains `vehicles` (filter options) and `allowedActions` (page).
- New: `SpkDetailSchema` with `steps`, `approvals` and `costs`.

### Web

- **SpkList.** Tabs with counts; a filter row (search, type, vehicle); a plain table, because
  server-side pages cannot use the client-side `DataTable` search.
- **Columns.** SPK with its urgency pill, Vehicle, Type, Status pill, Current step, Waiting on, and
  the action: Open for the creator's Draft or Rejected SPK (to Create SPK), View for everything else
  (to SPKDetail).
- **Pages.** 10, 20, 50 or 100 per page, Previous, Next, and "Page n of m (total)". Create SPK appears
  when the page allows `create`.
- **SpkDetail** (`/spk/[id]`):
  - the header (crumb, number, title, status and urgency pills; the actions DEC-127 hides);
  - a subline (plate, class, odometer, created by, approved by);
  - the Steps tab: StepTracker and StepCards;
  - the History tab: When, Who, What, from spk_approvals;
  - beside the steps: the context card (odometer, cost so far) and the ApprovalBlock (creation and
    completion: stamp, name, role, time, Self-approved).
- **New components** (ui.md 7.5): `StepTracker`, `StepCard`, `ApprovalBlock` in `components/spk/`.
